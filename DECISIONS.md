# DECISIONS.md

Running log of key choices and why. Written for mentor conversations — plain language, one paragraph each.

## Python/FastAPI over Node

We chose Python + FastAPI for the backend over a Node/Express stack because FastAPI gives us automatic request validation (via Pydantic) and interactive API docs for free, which matters a lot when a small team is moving fast under hackathon time pressure — every route gets typed input validation and clear error messages with almost no extra code. Python also made sense given the ML-adjacent features on the roadmap (adaptive difficulty, skill-gap scoring): even though our actual ML logic ended up being simple rule-based scoring rather than trained models, staying in Python kept the door open for scikit-learn without a language boundary between "the API" and "the ML."

## SQLite over Postgres

SQLite was chosen purely for hackathon speed: zero setup, no separate database server to run or configure, and the whole database is a single file that's trivial to reset between demos or tests. We deliberately used SQLAlchemy as the ORM specifically so this choice is cheap to reverse — swapping to Postgres later is a one-line change to `DATABASE_URL` plus adding a real migration tool (Alembic), not a rewrite of any query logic, since we never wrote raw SQL. This is explicitly flagged as a shortcut we would not make for a real production deployment — SQLite doesn't handle concurrent writes well at scale, which matters the moment multiple learners are submitting quizzes simultaneously against a shared server process.

## The 4 AI/ML features

We picked four features that each demonstrate a different flavor of "smart" without over-engineering: **adaptive quiz difficulty** (a simple 3-rung rule-based ladder — correct answer steps difficulty up, wrong steps it down — deliberately not IRT or a trained model, because a hackathon judge needs to understand the logic in one sentence and it needs to be debuggable at 2am); **skill-gap → job-readiness matching** (planned: a hand-set weighted-average scoring model comparing quiz performance against a few defined skill categories and sample job profiles — explainable by design, with a trained model only considered later if the simple version proves insufficient); **auto-generated practice questions** (planned: calling an external LLM API on module content, the one genuinely generative feature, with graceful degradation if the API is unavailable so the UI never crashes from a third-party outage); and **peer-benchmarking** (planned: plain SQL aggregation for percentile ranking against an anonymized cohort — explicitly not an ML problem, so we're not forcing a model where a `COUNT`/`AVG` query does the job). The common thread: reach for the simplest technique that solves the actual problem, and only escalate to something more complex (a trained model) if the simple version demonstrably falls short.

## Credentialed certification approach (UUID + PDF + QR + verify)

The core design goal was that a certificate must not be forgeable by editing a PDF. We solved this by making the PDF itself carry no authority — it's cosmetic. The only thing that matters is a UUID, stored once in the database alongside the learner and course it belongs to. The PDF embeds a QR code linking to a public `/verify/{uuid}` page that queries the database live, every time, and shows whatever the database currently says — learner name, course, issue date, validity. If someone edited a downloaded PDF to change the name on it, the QR code would still resolve to the real record and immediately expose the mismatch. Certificates auto-issue the moment a learner passes every quiz in a course (checked idempotently after each quiz submission) rather than requiring a manual "claim" step, because that removes an entire class of "why didn't I get my certificate" support questions.

## Design system direction (Midnight/Daylight Editorial via Superdesign)

We used the **Superdesign** CLI/tool to explore and generate the visual design system before writing any component code, rather than styling pages ad hoc as we built them. The direction went through two iterations: an initial light, forest-green "Editorial Tech" system (chosen because the real TISS logo's brand color is `#008000` green, so a muted-green accent was genuinely on-brand), then a deliberate pivot to "Midnight Editorial" — a bold, high-contrast, dark-first aesthetic (near-black background, coral accent) with a required light-mode counterpart ("Daylight Editorial") sharing the exact same layout, just different color tokens, switchable via a persisted toggle. The design system doc (`.superdesign/design-system.md`) explicitly documents where we deviated from initial visual references to fix accessibility problems — e.g., the reference implementation's low-contrast grays failed 4.5:1 contrast on the dark background, so we defined a separate "true decoration only" token and a genuinely-readable "muted text" token, and enforced that rule everywhere. This choice (design system first, as a written contract, before component code) meant the four core screens ended up visually consistent rather than each looking like it was styled by a different session.
